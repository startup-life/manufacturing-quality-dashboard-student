# 5회차 보충 문서: 검사기준 대조와 NotebookLM

이 문서는 AI 도구가 코드를 만들 때 읽는 자료입니다. 수강생은 이해하지 않아도 됩니다.

- 프롬프트가 요청한 일만 합니다. 이 문서의 내용을 한 번에 모두 만들지 않습니다.
- 앞 회차 문서와 다르면 번호가 큰 문서를 따릅니다. 이 회차가 바꾸는 앞 회차 약속: 보고서 검토 대기 기준(4회차 문서 "다시 판독 필요와 검토 대기"의 "검토 대기")은 이 문서 "홈과 2번 탭 배지"의 기준으로 바꿉니다. 2번 탭 배지(4회차에 만든 배지)는 이 문서 "홈과 2번 탭 배지"의 순서를 따릅니다. Google 쪽 일 목록(3회차 문서의 "Google 쪽 일 여섯 가지", 4회차 문서의 "Google 쪽에 더할 일")에 이 문서 "Google 쪽 코드"의 네 가지를 더합니다. 시트의 탭 목록(3회차 문서의 "Google 쪽 일 여섯 가지"와 "서버가 Google을 쓰는 법", 4회차 문서의 "판독 결과와 저장")에 이 문서 "근거 답과 대조 기록 저장"의 두 탭을 더합니다. 지시문 주소와 수정본 파일(4회차 문서의 "원문 파일과 수정본")은 이 문서 "근거 질문 저장"의 종류 이름을 받습니다. 2번 탭 상태 답(4회차 문서 "진행 상태와 잠금"의 `GET /api/inspections/(검사번호)/gemini`)과 판독 시작의 답에는 이 문서 "홈과 2번 탭 배지"의 `link` 항목을 더합니다. 4회차까지 안내 글만 있던 3번 탭은 이 문서 "3번 탭: 근거 확인"과 "3번 탭: 출처 대조"대로 채웁니다. Google 쪽 계산(4회차 문서의 "다시 판독 필요와 검토 대기")은 이 문서 "Google 쪽 코드"의 "다른 일"을 따릅니다.
- 맨 끝의 끝 표시를 만들어 `AGENTS.md`가 말한 대로 답의 마지막 줄에 적습니다.

## 이번 회차가 끝나면 되는 것

검사 상세 3번 탭에서 "근거 확인"을 누르면 내 NotebookLM 노트북(교육용 검사기준 Rev.A·Rev.B)에 질문하고, 답과 검사기준 원문을 함께 보여 줍니다. 답을 원문과 대조해 "일치" 또는 "검토 필요"로 저장하면 2번 탭 배지와 홈 "보고서 검토 대기"가 그 기록을 따릅니다. 설정 화면에서 근거 질문(v1~v3)을 고쳐 저장합니다.

## 스위치와 연동 상태 줄

NotebookLM 근거 대조 스위치는 `.env`의 `NOTEBOOKLM_MODE`입니다. 서버를 켤 때 한 번 읽습니다. 프롬프트의 "근거 확인이 꺼져 있으면"은 `NOTEBOOKLM_MODE=off`, "근거 확인이 연습용이면"은 `NOTEBOOKLM_MODE=mock`, "근거 확인 설정 값"은 `NOTEBOOKLM_MODE` 값을 말합니다.

| 값 | 뜻 |
|---|---|
| `off` | 꺼짐 |
| `mock` | 모의 응답 |
| `live` | 실제 질의 |

| 경우 | 약속 |
|---|---|
| `NOTEBOOKLM_MODE` 줄이 없음, `STORAGE_MODE=mock` | `mock`으로 봅니다 |
| `NOTEBOOKLM_MODE` 줄이 없음, `STORAGE_MODE=live` | `off`로 봅니다 |
| `STORAGE_MODE=live`에 `mock`을 적음 | `STORAGE_MODE=live`에서는 `mock`을 쓰지 않습니다(모의 근거가 실제 기록에 섞이지 않게). 서버를 켜지 말고 고칠 방법을 한국어 한 줄로 알립니다 |
| `off`·`mock`·`live`가 아닌 값 | 서버를 켜지 말고 고칠 방법을 한국어 한 줄로 알립니다 |

서버를 켤 때 서버 창에 아래 모양의 한 줄을 보여 줍니다. 이 줄은 이 절에서 새로 만듭니다. 저장소 줄은 그대로 둡니다. Gemini를 따로 알리는 줄이 있으면 그것도 그대로 둡니다.

```text
연동 상태: 저장소=값(뜻) · Gemini=값(뜻) · NotebookLM=값(뜻)
```

| 항목 | 값 | 뜻 |
|---|---|---|
| 저장소 | `mock` | 로컬 파일 |
| 저장소 | `live` | GAS 웹앱 |
| Gemini | `off` | 사람이 직접 판정 |
| Gemini | `mock` | 모의 초안 |
| Gemini | `live` | GAS에서 OnePort로 Gemini 호출 |
| NotebookLM | `off` | 근거 대조 꺼짐 |
| NotebookLM | `mock` | 모의 응답 |
| NotebookLM | `live` | 실제 질의 |

## NotebookLM 도구 부르기

| 항목 | 약속 |
|---|---|
| 도구와 버전 | `notebooklm-mcp-cli` 0.15.6으로 고정합니다 |
| 설치와 로그인 | 설치(`uv tool install`)와 로그인(`nlm login`)은 사용자가 직접 합니다. 실행하지 마세요. `nlm` 명령과 도구 실행 파일을 직접 실행해 보지 않습니다. 서버 코드가 띄우도록 만들기만 합니다 |
| 노트북 ID와 경로 받기 | 사용자가 채팅으로 준 노트북 ID와 도구 실행 파일 경로는 `.env`의 아래 두 줄에 넣습니다. 앞뒤에 공백이나 따옴표를 넣지 않습니다 |
| 서버 창에 내지 않는 값 | 노트북 ID, 도구 실행 파일 경로, `nlm` 출력은 서버 창과 화면에 옮겨 적지 않습니다 |
| 노트북 ID | `.env`의 `NOTEBOOKLM_NOTEBOOK_ID` |
| 도구 실행 파일 | `.env`의 `NOTEBOOKLM_MCP_COMMAND`(`notebooklm-mcp.exe` 전체 경로) |
| 패키지 | 더하지 않습니다 |
| 실행 방식 | 서버는 질문할 때마다 그 실행 파일을 띄우고 MCP(stdio, 줄 단위 JSON-RPC)로 `notebook_query` 도구 하나만 부른 뒤 끕니다 |
| 인자 | 실행 파일을 띄울 때 인자로 `--transport stdio`를 넘깁니다 |
| 넘기는 값 | `notebook_query`에는 `notebook_id`(노트북 ID)와 `query`(질문 글)를 넘깁니다 |
| 쓰는 값 | 돌아온 결과의 `answer`(답 글)와 `sources_used`(인용한 소스)를 씁니다. `sources_used`는 긴 번호로 오므로 화면에는 개수만 보여 줍니다 |
| 환경 변수 | 실행 파일에는 컴퓨터 기본 환경 변수(`PATH`, `USERPROFILE`, `APPDATA` 등)는 그대로 넘기고, 서버의 비밀값(OnePort 키, Google 웹앱 주소, 로그인 비밀값)만 뺍니다. `NOTEBOOKLM_HL=ko`와 `NOTEBOOKLM_RATE_LIMIT_MAX_RETRIES=0`(한도에 걸려도 다시 시도하지 않기)을 넘깁니다 |
| 기다리는 시간 | 서버는 답을 150초까지 기다립니다 |

줄 단위 JSON-RPC는 이 순서입니다.

1. `initialize`를 보냅니다(`id` 1, `params`는 `{"protocolVersion": "2025-03-26", "capabilities": {}, "clientInfo": {"name": "tumbler-factory", "version": "0.1.0"}}`).
2. 그 답이 오면 `notifications/initialized`를 보낸 뒤 `tools/call`을 보냅니다(`id` 2, `params`는 `{"name": "notebook_query", "arguments": {"notebook_id": 노트북 ID, "query": 질문 글}}`).
3. `id` 2의 답에서 `result.structuredContent`를 읽습니다. 없으면 `result.content`의 글을 JSON으로 읽습니다. 그 안의 `status`, `answer`, `sources_used`, `error_details.category`를 씁니다.

실패하면 아래 한 줄로 끝냅니다.

| 경우 | 문장 |
|---|---|
| 150초 안에 답이 오지 않음 | "NotebookLM 응답 시간이 초과되었습니다. 자동 재시도하지 않습니다." |
| 결과의 `status`가 `error`이고 `error_details.category`가 `deadline_exceeded`임(도구 자체 시간 한도) | 같은 시간 초과로 처리합니다. 문장도 같습니다 |
| 그 밖의 실패(실행 파일을 띄우지 못함, `.env`의 두 값이 비어 있음, 답 글이 비어 있음 포함) | "NotebookLM 질문에 실패했습니다. 로그인과 노트북 ID를 확인하세요." |

## 원문 파일

NotebookLM에 올리는 검사기준 원문은 `standards/notebooklm-Rev.A.md`, `standards/notebooklm-Rev.B.md`입니다. 4회차 검사기준 원문과 같은 내용이고 문서번호 `TUM-QC-STD-001`과 버전이 들어 있습니다. 4회차 문서의 "추가 정보"에서 복사한 파일이며, 없으면 그 절대로 복사합니다.

| 주소 | 하는 일 | 답 |
|---|---|---|
| `GET /api/standards/Rev.A/text` (또는 `Rev.B`) | 3번 탭에서 읽을 검사기준 원문 글 | `{"revision": 기준 버전, "text": 원문 글}`. 다른 기준 이름이면 "검사기준을 찾을 수 없습니다." |

## 질문 글

질문 글은 여섯 덩어리를 이 순서로 잇습니다.

1. 안전 문구 글
2. `[근거 질문]`
3. 고른 근거 질문 원문
4. `[검사 정보]`
5. 검사 정보 글(제품, 중량, 기준 버전). 꼴: `제품: 텀블러 실버 (P-SILVER) / 중량: 352g / 적용 검사기준 버전: Rev.A`. 제품이 없으면 "제품 미지정", 중량이 없으면 "미측정"입니다
6. 조회 줄 글

모든 덩어리 사이에는 빈 줄 하나를 둡니다. 제목 줄 `[근거 질문]`·`[검사 정보]`와 그 본문 사이도 빈 줄 하나입니다.

안전 문구와 조회 줄의 글은 아래 추가 정보 파일에 있습니다. "안전 문구:", "조회 줄:"은 이름표입니다. 질문 글과 화면에는 이름표를 빼고 그 뒤의 글만 넣습니다. 조회 줄 글은 "조회할 원문: TUM-QC-STD-001 Rev.A."로 시작하고, Rev.A 자리에는 그 검사의 기준 버전을 넣습니다.

안전 문구와 조회 줄이 든 추가 정보 파일은 아래 표와 같습니다. 파일은 `docs/guide/files/reference/`에 있고 프롬프트나 이 문서가 가리킬 때만 엽니다. 앱 폴더로 복사하지 않습니다.

| 프롬프트에서 부르는 이름 | 종류 | 파일 | 쓰는 법 |
|---|---|---|---|
| 안전 문구, 조회 줄 | 참고 | `docs/guide/files/reference/notebooklm-fixed-text.md` | 코드 속 글로 씁니다. 이름표를 뺀 글은 글자 그대로 씁니다 |

## 근거 질문 저장

근거 질문은 4회차 지시문 저장 방식(4회차 문서의 "원문 파일과 수정본")을 그대로 쓰고 종류 이름은 `notebooklm`입니다(v1~v3 원문과 수정본). 고르지 않으면 v3 기본 원문을 씁니다. Gemini 지시문의 종류 이름은 `gemini`입니다.

| 항목 | 약속 |
|---|---|
| 기본 원문 | `prompts/notebooklm-v1.md`, `notebooklm-v2.md`, `notebooklm-v3.md` |
| 수정본 파일 | Gemini 지시문과 같은 `runtime/custom-prompts.json`에 쌓습니다. 안은 `[{"name": 이름, "text": 글, "kind": 종류 이름}, ...]` 모양이고, `kind`가 없는 수정본은 `gemini`로 봅니다 |
| 수정본 이름 | 4회차와 같은 꼴입니다. 맨 앞은 고쳐 쓴 근거 질문의 v1~v3입니다 |
| 설정 화면 | 4회차에 만든 Gemini 판독 지시문 칸 아래에 같은 모양의 "NotebookLM 근거 질문" 칸을 둡니다. 버전을 고르면 글이 보이고(처음 값은 v3), 고친 글은 "수정본 저장"으로 새 수정본이 됩니다. 저장하면 3번 탭의 근거 질문 고르는 칸에도 그 수정본이 생깁니다 |

| 주소 | 하는 일과 요청 | 답 |
|---|---|---|
| `GET /api/prompts?kind=notebooklm` | 근거 질문 목록(기본 원문 v1~v3 다음에 수정본). `kind`를 빼면 `gemini`입니다 | 4회차 문서의 "원문 파일과 수정본"과 같은 모양입니다 |
| `POST /api/prompts` | 수정본 저장. 요청은 `{"base": 고쳐 쓴 버전 이름, "text": 글, "kind": 종류 이름}`이고 `kind`를 빼면 `gemini`입니다 | 4회차 문서의 "원문 파일과 수정본"과 같은 모양입니다 |

## 모의 답

`NOTEBOOKLM_MODE=mock`이면 NotebookLM에 묻지 않고 모의 답을 만들고, 모의 답이라는 표시를 붙입니다(근거 답의 `mode`가 `mock`).

모의 답 글은 아래 모양입니다.

```text
Rev.A 표준서 원문: "…" (출하 승인 없음, 담당자 대조 확인 필요)
```

"…" 자리에는 그 기준 버전의 검사기준 원문에서 외관 기준 문장 하나(`## 2. 외관 기준` 절의 첫 문장)를 그대로 따와 넣고, Rev.A 자리에는 기준 버전을 넣습니다. 화면은 모의 답에 노란 "모의 응답 — 실제 NotebookLM 연결 아님"을 보여 줍니다.

## 근거 확인 조건

| 항목 | 약속 |
|---|---|
| 묻는 때 | 근거 질문은 `NOTEBOOKLM_MODE`가 `off`가 아니고, 그 검사의 최신 판독 결과(AI 초안)가 있고 "다시 판독 필요"가 아닐 때만 합니다. 최신 판독 결과는 4회차 문서 "판독 결과와 저장"의 판독 결과 가운데 가장 최근 것이고, "다시 판독 필요"는 4회차 문서 "다시 판독 필요와 검토 대기"의 뜻입니다 |
| 기준 버전 | 그 판독 결과의 기준 버전입니다 |
| 2번 탭과 같이 | 3번 탭은 2번 탭과 같은 최신 판독 결과를 쓰고, 2번 탭이 새 결과를 받으면 함께 다시 그립니다 |
| 여는 때 | 3번 탭을 열 때마다 아래 `GET` 주소로 상태를 다시 묻고 버튼과 안내를 새로 그립니다. 1번 탭에서 제품·중량·사진을 고친 뒤 3번 탭을 열면 새 상태를 따릅니다 |

| 주소 | 하는 일과 요청 | 답 |
|---|---|---|
| `POST /api/inspections/(검사번호)/evidence` | 근거 묻기. 요청은 `{"prompt": 근거 질문 이름}`이고 빼면 v3입니다. 묻지 않는 경우에는 1회차 문서 "서버 오류 문장"의 오류 모양으로 안내합니다 | 저장한 근거 답 한 건("근거 답과 대조 기록 저장") |
| `GET /api/inspections/(검사번호)/evidence` | 3번 탭이 묻는 상태 | 아래 표의 항목입니다 |

| 항목 | 값 |
|---|---|
| `mode` | 지금 `NOTEBOOKLM_MODE` 값("연결 상태") |
| `revision` | 최신 판독 결과의 기준 버전. 없으면 그 검사의 기준 버전 |
| `has_result` | 판독 결과가 있으면 `true` |
| `stale` | 가장 최근 결과가 "다시 판독 필요"면 `true` |
| `query` | 최신 판독 결과로 물은 마지막 답. 없으면 `null` |
| `link` | 그 답의 마지막 대조 기록. 없으면 `null` |

두 주소 모두 검사가 없으면 "검사를 찾을 수 없습니다."입니다.

## 근거 답과 대조 기록 저장

근거 답은 시트 탭 `evidence_queries`에, 출처 대조 기록은 시트 탭 `evidence_links`에 저장합니다. 탭이 없으면 만들고(첫 줄은 열 이름), 필요한 열이 없으면 끝에 더합니다. 내 컴퓨터 저장(`STORAGE_MODE=mock`)도 같은 이름을 씁니다. 파일은 `runtime/evidence-queries.json`, `runtime/evidence-links.json`이고 안은 한 건의 목록입니다.

근거 답 한 건의 모양입니다.

```json
{"query_id": "EQ-3fa9c1d2", "inspection_id": "INSP-20261029-3fa9c1d2", "draft_id": "GR-3fa9c1d2", "created_at": "2026-10-29 14:07:21", "mode": "live", "revision": "Rev.A", "prompt_name": "v3", "question": "보낸 질문 전체", "answer": "답 글", "sources": ["인용한 소스 번호"]}
```

출처 대조 기록 한 건의 모양입니다.

```json
{"link_id": "EL-3fa9c1d2", "query_id": "EQ-3fa9c1d2", "inspection_id": "INSP-20261029-3fa9c1d2", "draft_id": "GR-3fa9c1d2", "status": "VERIFIED_BY_USER", "memo": "", "user": "writer", "created_at": "2026-10-29 14:09:02"}
```

| 항목 | 약속 |
|---|---|
| `query_id`, `link_id` | 서버가 만듭니다. 모양은 `EQ-xxxxxxxx`, `EL-xxxxxxxx`입니다(x는 0~9·a~f 8글자) |
| `draft_id` | 판독 결과 번호입니다. 4회차 문서 "판독 결과와 저장"의 `result_id` 값을 넣습니다 |
| `created_at` | 한국 시각 "YYYY-MM-DD HH:MM:SS" 글입니다 |
| `mode` | 근거 답의 방식입니다. `mock` 또는 `live`입니다 |
| `prompt_name` | 고른 근거 질문의 버전 이름입니다 |
| `sources` | `sources_used`의 목록입니다. 시트 칸에는 JSON 글로 적고, 읽을 때 목록으로 되돌립니다 |
| `user` | 로그인한 사용자 이름입니다 |

시트의 머리글은 위 모양의 칸 이름을 같은 순서로 씁니다.

| 탭 | 머리글 |
|---|---|
| `evidence_queries` | `query_id`, `inspection_id`, `draft_id`, `created_at`, `mode`, `revision`, `prompt_name`, `question`, `answer`, `sources` |
| `evidence_links` | `link_id`, `query_id`, `inspection_id`, `draft_id`, `status`, `memo`, `user`, `created_at` |

대조 기록에는 어느 답(`query_id`)과 어느 판독 결과(`draft_id`)를 대조했는지, 대조 결과, 메모, 로그인한 사용자 이름, 저장 시각을 남깁니다.

- 기록은 자기가 대조한 답에만 붙고, 같은 판독 결과로 새로 물은 답은 아직 대조 전입니다.
- 마지막 대조 기록은 최신 판독 결과에 붙은 기록입니다.

대조 결과 이름(`status`)입니다.

| 대조 결과 | 실제 답을 대조함 | 모의 답을 대조함 | 화면 글 |
|---|---|---|---|
| 일치 | `VERIFIED_BY_USER` | `MOCK_USER_REVIEWED` | "일치" |
| 검토 필요 | `REVIEW_NEEDED_BY_USER` | `MOCK_REVIEW_NEEDED` | "검토 필요" |

| 주소 | 하는 일과 요청 | 답 |
|---|---|---|
| `POST /api/inspections/(검사번호)/evidence-link` | 대조 기록 저장. 요청은 `{"verdict": "match"(일치) 또는 "review"(검토 필요), "memo": 글}`입니다 | 저장한 대조 기록 한 건. 검사가 없으면 "검사를 찾을 수 없습니다." 최신 판독 결과로 물은 답이 없으면 저장하지 않고 "근거 확인을 먼저 하세요." |

## 홈과 2번 탭 배지

홈 "보고서 검토 대기"는 최신 판독 결과가 있는 검사 가운데 아래 셋 중 하나인 검사를 셉니다.

- 그 판독 결과의 대조 기록이 없습니다.
- 마지막 대조 기록이 검토 필요입니다.
- 판독 결과가 "다시 판독 필요"입니다.

마지막 기록이 일치면 빠집니다. 판독 결과가 없는 검사는 세지 않습니다. `GET /api/home`의 `review_pending`과 `GET /api/inspections`의 `review=pending`이 이 기준을 씁니다.

2번 탭 배지도 같은 기록을 따르고, 위에서부터 먼저 맞는 것을 씁니다.

| 순서 | 경우 | 배지 |
|---|---|---|
| 1 | 판독 중 | "판독 중" |
| 2 | 판독 실패 | "판독 실패" |
| 3 | 판독 결과가 없음 | "결과 없음" |
| 4 | 최신 판독 결과가 "다시 판독 필요"(대조 기록이 무엇이든) | "다시 판독 필요" |
| 5 | 마지막 대조 기록이 검토 필요 | "검토 필요"(노랑) |
| 6 | 그 밖(일치 기록이나 기록 없음) | "확인할 결과" |

3번 탭에서 대조 기록을 저장하면 2번 탭 배지를 새로고침 없이 바로 이 순서대로 다시 정합니다.

2번 탭 상태 답(4회차 문서의 "진행 상태와 잠금")에 아래 항목을 더합니다. 앞의 항목은 그대로 둡니다.

| 항목 | 값 |
|---|---|
| `link` | 최신 판독 결과의 마지막 대조 기록. 없으면 `null` |

## 연결 상태

3번 탭이 쓰는 연결 정보는 지금 근거 확인 설정 값 하나입니다. `GET /api/inspections/(검사번호)/evidence` 답의 `mode`에 `NOTEBOOKLM_MODE` 값(`off`, `mock`, `live`)을 넣고, 3번 탭은 이 값이 `off`면 "근거 확인"을 끕니다("3번 탭: 근거 확인"). 실제 질의가 되는지는 답 상자와 실패 문장으로 봅니다.

## Google 쪽 코드

Google 쪽(Apps Script)에 필요한 일은 네 가지입니다. "답"은 `{"ok": true, "data": 결과}`의 `data`입니다.

| 일 | 일 이름 | 요청에 더하는 값 | 하는 일 | 답 |
|---|---|---|---|---|
| 근거 답 저장 | `saveEvidenceQuery` | `{"record": 근거 답 한 건}`. `sources`는 JSON 글입니다 | `evidence_queries` 탭에 한 줄을 더합니다 | `{"saved": 1}` |
| 한 검사의 근거 답 꺼내기 | `listEvidenceQueries` | `{"inspection_id"}`. 빼면 모든 검사의 답입니다 | `evidence_queries` 탭을 읽습니다 | `{"queries": [탭 줄, ...]}` |
| 대조 기록 저장 | `saveEvidenceLink` | `{"record": 대조 기록 한 건}` | `evidence_links` 탭에 한 줄을 더합니다 | `{"saved": 1}` |
| 대조 기록 꺼내기 | `listEvidenceLinks` | `{"inspection_id"}`. 빼면 모든 검사의 기록입니다 | `evidence_links` 탭을 읽습니다 | `{"links": [탭 줄, ...]}` |

| 항목 | 약속 |
|---|---|
| 이미 있는 일 | 같은 일을 하는 것이 이미 있으면(예: 판독 결과별 대조 기록 꺼내기) 새로 만들지 말고 그것을 씁니다 |
| 한 번에 읽기 | 2번 탭 상태처럼 판독 결과와 대조 기록을 함께 쓰는 요청은 Google을 한 번만 부릅니다(여러 탭을 한 번에 읽는 일, 3회차 문서 "Google 쪽 일 여섯 가지"의 `read`로 함께 읽습니다). `read`는 칸에 적힌 글을 그대로 돌려줍니다. 그래서 `read`로 읽은 `gemini_results`의 `images`·`result`와 `evidence_queries`의 `sources`는 JSON 글이고, 서버에서 목록과 객체로 되돌린 뒤 씁니다(`listGeminiResults`로 읽은 판독 결과와 같은 모양) |
| 이름 짓는 방식 | 새 일 이름은 Google 쪽 코드에 이미 있는 이름 짓는 방식을 따릅니다. 3회차와 4회차 문서의 이름(`savePhoto`, `saveGeminiResult`, `listGeminiResults`)대로면 위 표의 이름입니다. 점으로 나누는 방식이면 `evidence.queries.save`처럼 그 방식을 따릅니다. 이미 있는 방식이 없을 때만 `evidenceQuerySave`, `evidenceQueryList`, `evidenceSave`, `evidenceList` 같은 이름을 예로 씁니다 |
| 요청 방식 | 새 일은 Google 쪽 코드에 이미 있는 요청 방식(일 이름을 받아 나눠 처리하는 곳)을 그대로 따라 더합니다 |
| 앞 회차 이름 | 앞 회차의 일 이름·탭 이름·파일 이름은 바꾸지 않습니다 |
| 시트 만들기 | 두 탭과 머리글("근거 답과 대조 기록 저장")은 Google 쪽 시트 만들기(`setup`) 목록에 더해, `npm.cmd run gas:init`을 다시 실행하면 빠진 탭·칸이 생기게 합니다(이미 있으면 그대로) |
| 올리기 | Google 쪽 코드를 올리는 명령(`npm.cmd run gas:push`)에 새 코드가 빠지지 않게, 지금 올라가고 있는 Google 쪽 코드에 더합니다. 새 파일을 만들었다면 올리는 명령에 그 파일이 들어가는지 확인합니다 |
| 다른 일 | 화면과 서버의 다른 일을 만들 때는 Google 쪽 코드를 고치지 않습니다. 답에 대조 기록 붙이기, 2번 탭 상태, 검토 대기 세기는 위 네 가지와 `read`로 읽은 줄을 서버에서 걸러 만듭니다 |

## 3번 탭: 근거 확인

3번 탭은 검사 상세의 "③ 검사기준과 비교하기" 탭입니다. 4회차까지 있던 안내 글은 지우고, 위에서부터 아래 순서로 놓습니다. 3번 탭을 열 때마다 `GET /api/inspections/(검사번호)/evidence`로 상태를 묻고 새로 그립니다("근거 확인 조건").

3번 탭은 이 상태 주소와 `link`를 더한 2번 탭 상태(4회차 문서 "진행 상태와 잠금")를 화면에서 처음 쓰는 곳입니다. 접힌 원문 칸도 이 상태 답의 `revision`을 받은 뒤에 원문을 부르므로, 상태 주소가 실패하면 원문 대신 "서버에서 오류가 발생했습니다."가 나옵니다. 서버의 공통 오류 처리(`src/api-exception.filter.ts`)는 `HttpException`이 아닌 예외를 서버 창에 적지 않고 이 문장으로 바꾸므로, 서버 창에 빨간 글이 없어도 서버 코드의 예외입니다. 원문 파일 위치보다 상태 주소를 먼저 의심합니다.

그래서 3번 탭을 만드는 요청에서는 화면만 더하지 않고, 2번 탭 상태를 만드는 서버 코드(`src/gemini-result.store.ts`의 `getStatus`)를 먼저 엽니다. Google 저장(`STORAGE_MODE=live`)에서 `read`로 읽은 `gemini_results` 줄의 `result`·`images`를 JSON 글 그대로 판독 결과 검사(`normalizeGeminiResult`)에 넘기고 있으면, 검사가 `null`을 돌려 "저장된 판독 결과를 읽을 수 없습니다." 예외가 납니다. 이때는 그 자리에서 글을 먼저 풀도록 함께 고칩니다("Google 쪽 코드"의 "한 번에 읽기"). 서버를 켜서 볼 수 있으면 판독 결과가 있는 검사로 `GET /api/inspections/(검사번호)/evidence`와 `GET /api/inspections/(검사번호)/gemini`가 오류 없이 답하는지 봅니다.

코드 참고: 4회차 완료 코드(`class/milestone-4`)에서는 `src/gemini-result.store.ts`의 `getStatus`가 `readResults`를 거쳐 Google 쪽 `listGeminiResults`로 읽었고, JSON 글은 `gas/Code.js`의 `parseGeminiJsonCell`이 풀었습니다. `read`는 이 풀기를 하지 않으므로 서버에서 아래만큼 더합니다. 적용 범위는 `read`로 읽은 판독 결과 줄을 판독 결과 모양으로 바꾸는 한 곳이고, 화면과 Google 쪽 코드는 고치지 않습니다.

```ts
const parseCell = (value: unknown): unknown => {
  if (typeof value !== 'string') return value;
  try { return JSON.parse(value); } catch { return value; }
};
const result = normalizeGeminiResult(parseCell(record.result));
const images = parseCell(record.images); // 목록이면 글자만 남겨 씁니다
```

| 순서 | 놓을 것 | 약속 |
|---|---|---|
| 1 | 제목 "검사기준과 비교하기" | |
| 2 | 접힌 "검사기준 원문 읽기 · Rev.A" | Rev.A 자리에는 상태 답의 `revision`을 넣습니다. 펼치면 "원문 파일"의 주소로 받은 그 기준 버전의 원문 글을 보여 줍니다 |
| 3 | "NotebookLM 근거 질문" 고르는 칸 | `GET /api/prompts?kind=notebooklm`의 목록입니다("근거 질문 저장"). 처음 값은 v3 기본 원문입니다. 이름은 설정 화면의 고르는 칸과 같게 보입니다 |
| 4 | "근거 확인" 버튼 | 누르면 고른 근거 질문 이름으로 `POST /api/inspections/(검사번호)/evidence`를 보냅니다 |
| 5 | 안내 글 | 버튼을 끈 까닭을 보여 줍니다. 버튼이 켜져 있으면 비워 둡니다 |
| 6 | 답 상자 | 근거 답의 `answer`를 글자로 넣습니다("화면 안전"). 그 아래에 인용한 소스 개수를 "인용한 소스 2개"처럼 적습니다. 모의 답이면 노란 "모의 응답 — 실제 NotebookLM 연결 아님"을 함께 보여 줍니다("모의 답") |
| 7 | 접힌 "NotebookLM에 보낸 질문 보기" | 펼치면 근거 답의 `question`(보낸 질문 전체)을 보여 주고, 맨 아래에 "사용한 근거 질문: v3 · 기본 원문"을 적습니다. 수정본으로 물었으면 날짜 없이 "v3 · 저장한 수정본"으로 적습니다(v3 자리는 고쳐 쓴 버전) |
| 8 | 출처 대조 칸 | "3번 탭: 출처 대조" |

"근거 확인" 버튼을 끄는 때와 안내 글입니다. 위에서부터 먼저 맞는 것을 씁니다. 버튼을 꺼도 검사기준 원문은 그대로 펼쳐 읽을 수 있습니다.

| 상태 답 | 버튼 | 안내 글 |
|---|---|---|
| `mode`가 `off` | 끔 | "NotebookLM 근거 대조가 꺼져 있습니다(NOTEBOOKLM_MODE=off). 기준 원문을 직접 읽고 판단하세요." |
| `has_result`가 `false` | 끔 | "2번 탭에서 판독 결과를 먼저 준비하세요. 결과가 생기면 근거를 볼 수 있습니다." |
| `stale`이 `true` | 끔 | "2번 탭에서 다시 판독해 주세요. 이전 결과로는 근거를 확인할 수 없습니다." |
| 그 밖 | 켬 | 없음 |

"근거 확인"을 누르면 아래와 같이 합니다.

| 때 | 화면 |
|---|---|
| 기다리는 동안 | 답 상자 자리에 "NotebookLM에서 검사기준을 찾는 중입니다."를 보이고 버튼을 끕니다 |
| 답이 옴 | 답 상자, 보낸 질문 보기, 빈 출처 대조 칸을 새로 그리고 버튼을 다시 켭니다 |
| 실패 | "근거 확인 실패: " 뒤에 서버가 준 문장을 붙여 보여 주고 버튼을 다시 켭니다 |

상태 답의 `query`가 있으면(최신 판독 결과로 이미 물은 답) 3번 탭을 열 때 그 답과 보낸 질문 보기, 출처 대조 칸을 바로 보여 줍니다. 상세를 다시 열거나 서버를 다시 켜도 마지막 답이 남아 보이는 것은 이 때문입니다.

| 저장 버튼 | "출처 대조 기록 저장" |

| 항목 | 약속 |
|---|---|
| 버튼 켜기 | 첫 체크칸을 체크해야 저장 버튼이 켜집니다 |
| 보내는 값 | 둘째 칸도 체크했으면 `{"verdict": "review"}`(검토 필요), 아니면 `{"verdict": "match"}`(일치)에 메모를 붙여 `POST /api/inspections/(검사번호)/evidence-link`로 보냅니다 |
| 저장한 뒤 | 버튼 글을 "기준 확인 기록 저장됨"으로 바꾸고 버튼과 체크칸을 끕니다. 2번 탭 배지를 새로고침 없이 바로 다시 정합니다("홈과 2번 탭 배지") |
| 저장 실패 | 버튼 아래에 서버가 준 문장을 보여 주고 버튼을 다시 켭니다 |
| 다시 열 때 | 상태 답의 `link`가 지금 보이는 답(`query`)에 붙은 기록이면 체크칸을 그 기록대로 채우고(일치면 첫 칸, 검토 필요면 두 칸), 메모를 보이고, 버튼을 "기준 확인 기록 저장됨"으로 끈 채 둡니다. 같은 판독 결과로 새로 물은 답은 아직 대조 전이라 비어 있습니다 |

## 화면 안전

AI·NotebookLM이 준 글은 HTML로 넣지 말고 글자로 넣습니다.

## 만들지 않는 것

- 근거 질문의 접힌 "전달 내용 보기"(묻기 전에 보낼 글을 미리 보기): 혼자 쓰는 연습용 앱이라 만들지 않습니다. 물은 뒤의 "NotebookLM에 보낸 질문 보기"로 같은 글을 봅니다.
- 지난 근거 답 목록 주소(답마다 마지막 대조 기록 붙이기): 혼자 쓰는 연습용 앱이라 만들지 않습니다. 쓰는 화면이 없습니다.
- NotebookLM "연결됨" 추적(첫 성공 뒤에만 "정상 연결"), 연결 상태 주소(`GET /api/notebooklm/status`), 설정 화면의 "NotebookLM 연결 상태" 카드, 3번 탭의 연결 정보: 혼자 쓰는 연습용 앱이라 만들지 않습니다. 3번 탭은 `mode` 하나만 씁니다("연결 상태").
- 답 글 꾸미기(굵은 글, 목록, 인용, 기울임, 소제목, 구분선을 기호 없이 보이기): 혼자 쓰는 연습용 앱이라 만들지 않습니다. 답은 받은 글자 그대로 보여 줍니다("화면 안전").
- 2번 탭 배지 "대조 기록 확인 실패"와 2번 탭 상태 답의 `link_error`: 혼자 쓰는 연습용 앱이라 만들지 않습니다.
- 2번 탭 배지 "검토 필요(이전 버전)": 혼자 쓰는 연습용 앱이라 만들지 않습니다. 그때는 "다시 판독 필요"를 보여 줍니다.
- 2번 탭 배지 "확인하는 중"(불러오는 동안): 혼자 쓰는 연습용 앱이라 만들지 않습니다.
- 판독 중이거나 상태를 불러오기 전에 "근거 확인"을 끄고 "판독이 끝나면 누를 수 있다"고 안내하기, 3번 탭 상태 답(`GET /api/inspections/(검사번호)/evidence`)의 `running`: 혼자 쓰는 연습용 앱이라 만들지 않습니다.

끝 표시: `5회차-종이노트-` 뒤에 "NotebookLM 도구 부르기"의 도구 버전을 붙입니다.
